# Contributing to rmcloud-go

Thank you for your interest in contributing to rmcloud-go! This guide will help you get started.

## Prerequisites

- **Go 1.27+** — [download](https://go.dev/dl/)
- **Make** — for running project targets
- **Git** — for version control

## Getting Started

1. **Fork** the repository on GitHub.

2. **Clone** your fork:

   ```bash
   git clone https://github.com/<your-username>/rmcloud-go.git
   cd rmcloud-go
   ```

3. **Create a branch** from `develop`:

   ```bash
   git checkout -b feat/my-feature develop
   ```

4. **Make your changes**, then run checks:

   ```bash
   make fmt
   make lint
   make test-all
   ```

5. **Commit** using [Conventional Commits](#commit-messages) and push:

   ```bash
   git push origin feat/my-feature
   ```

6. **Open a Pull Request** against the `develop` branch.

## Branch Naming

Use the following prefixes:

| Prefix | Purpose |
|--------|---------|
| `feat/` | New features |
| `fix/` | Bug fixes |
| `docs/` | Documentation changes |
| `refactor/` | Code refactoring |

## Commit Messages

We follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>[(<scope>)][!]: <description>

[optional body]

[optional footer(s)]
```

**Types:** `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `perf`, `build`, `style`, `revert`

**Scope** is optional. When present, it must be listed in [`commit_scopes.txt`](commit_scopes.txt). Never use `root`; omit the scope for
repository-wide changes. Use `!` before the colon for a breaking change.

Describe the concrete change and its purpose. Keep the body only when it explains behavior or a decision beyond the subject. Do not include filler,
work logs, test results, coverage figures or validation summaries. Do not mention agents or AI assistance, add generation signatures, or add agent
co-author trailers. The same format and scope rules apply to PR titles. Merges generated by git (git flow releases and hotfixes) keep git's
subject.

Examples:

```
fix(syncstore): keep the generation on a retried root write
feat(auth): reject a user token without an expiry
refactor(syncstore): split the index reader
test(auth): cover an expired device token
docs(README): add quick start examples
build(devtools): bump golangci-lint
build(deps): bump golang.org/x/sys from 0.48.0 to 0.49.0
```

Dependabot opens its updates as `build(deps): bump …` (see [`.github/dependabot.yml`](.github/dependabot.yml)); they follow the same rules
and get no exemption.

### Automated Validation

- **GitHub Actions** automatically validates all commit messages and PR titles
- **Local validation** can be enabled with: `git config core.hooksPath .githooks`
- Run `bash .github/scripts/validate-commits.sh` to check your commits before pushing
- Run `bash .github/scripts/test-commit-validation.sh` after changing the validator or `commit_scopes.txt`

## Code Style

### Formatting

- Run `make fmt` before committing — this runs `golangci-lint fmt`, so the `gci` sections in `.golangci.yml` order the imports. Standalone
  gci v0.14.0 predates Go 1.27 and files the standard package `uuid` under default; only `make generate` runs it, on generated files.
- Maximum line length: **156 characters** (enforced by `lll` linter).

### Import Ordering

Imports must follow this order (enforced by `gci` via `.golangci.yml`):

1. Standard library
2. Third-party packages (default)
3. `google.golang.org`
4. `golang.org`
5. `github.com/altessa-s/go-atlas-core`
6. `github.com/altessa-s/go-atlas-net`
7. `github.com/altessa-s/rmcloud-go`
8. `github.com/altessa-s` (other altessa packages)
9. Blank imports
10. Aliases

### Copyright Headers

All `.go` files must include the copyright header. Run `make copyright` to add it automatically.

```go
// Copyright 2026 ALTESSA SOLUTIONS INC.
// Use of this source code is governed by the MIT license that can be found in
// the LICENSE file.
```

## Generated options

Package options are generated by [`optgen`](https://github.com/altessa-s/go-optgen) from the private `options` struct in each `options.go` into
`options_gen.go`. `make generate` builds the optgen and gci versions pinned in `devtools/go.mod` into `bin/`
and regenerates every package. When a change needs a new or changed option, edit the `options` struct and its `optgen` tags in `options.go`, run
`make generate`, and commit the regenerated `options_gen.go` in the same change. Never edit `options_gen.go` by hand.

## CI checks

CI requires at least 95% total statement coverage on Linux, and every protocol package listed in [`.coverage.yml`](.coverage.yml) must
stay at or above its threshold (`make coverage-gate`). Raise these floors as coverage improves; do not lower them to accommodate untested changes.
Every protocol scenario needs a negative test alongside the positive one. The full suite runs with the race detector and shuffled test order, and the platform-gated code is cross-compiled for darwin and
windows.

## Tests

| Kind | Files | Run with |
|------|-------|----------|
| Unit | `*_test.go` | `make test`, `make test-race`, `make coverage` |
| Integration | `*_integration_test.go`, first line `//go:build integration` | `make test-integration` |
| Benchmarks | `*_bench_test.go` | `make bench`, `make bench-count`, `make bench-compare` |
| Fuzz | `Fuzz*` targets in `*_test.go` | `make fuzz-seed`, `make fuzz` |

Unit tests never touch the network, the disk outside `t.TempDir()`, or the wall clock: they take the doubles in `internal/porttest`. Integration
tests drive the public facade and the real adapters against loopback servers (`httptest`, a real WebSocket server) and temporary directories, on
real timers; their lower time bounds are exact and their upper bounds carry slack. Nothing calls remarkable.com. Packages whose tests start
goroutines end the test binary with go-atlas-core's leak check, which covers the integration tests too. Benchmarks call `b.ReportAllocs()` and
`b.Loop()`, build fixtures outside the loop, and stay fast enough for `make bench-compare`, which the `Benchmarks` workflow runs on every pull
request.

## Fuzzing

`go test ./...` already executes every fuzz target over its `f.Add` seeds, so seeds act as ordinary regression cases and a PR needs nothing extra.
Mutation is separate: `make fuzz` walks each target for `FUZZTIME` (`go test -fuzz` accepts one target per package per invocation), and the `Fuzz`
workflow does the same nightly with 2m per target, restoring the generated corpus between runs so coverage compounds.

Write a fuzz target when the input is attacker-controlled or there is a property worth stating — a round trip, an allowlist that must hold, an
invariant the code documents. "Does not panic" is the floor, not the goal: a target with no assertion passes for the wrong reasons. When a run
fails, Go writes the minimized reproducer to the package's `testdata/fuzz/<Target>/`; commit it, so the case is pinned forever in the seed corpus.

## Pull Request Process

1. Ensure `make lint` and `make test-all` pass.
2. Write conventional commit messages: release notes are generated from them by goreleaser at release time, there is no
   manually maintained `CHANGELOG.md`.
3. Fill out the PR template completely.
4. One approving review is required before merging.
